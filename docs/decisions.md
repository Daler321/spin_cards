# Журнал решений

Решения по пробелам и неясностям `TZ.md`, а также технические выборы, которых нет в ТЗ.
Формат: контекст → решение → последствия. Новые записи добавляются в конец, старые не переписываются;
если решение меняется, заводится новая запись со ссылкой на старую.

## M0. Каркас и Docker (2026-10-12)

### D-001. Node.js 24 LTS вместо 20

ТЗ (раздел 3) называет Node 20, но его поддержка закончилась 30.04.2026. Берём Node 24 LTS
(поддержка до 04.2028): образ `node:24.21.0-alpine`, `.nvmrc` = 24, `engines.node >= 24`.

### D-002. React 19 вместо 18

ТЗ указывает React 18 «по умолчанию»; актуальная стабильная версия 19.3. Framer Motion,
TanStack Query и react-i18next её поддерживают. Берём React 19.

### D-003. TypeScript 6.0, не 7

TypeScript 7 (нативный компилятор) уже вышел, но `typescript-eslint` поддерживает TS `< 6.1`,
а без него нет type-aware линтинга. Берём `typescript ~6.0.3`; переход на 7 после поддержки в линтере.

### D-004. pnpm 10.34

Вышел pnpm 12, но на машине разработчика pnpm 10, и ветка 10 поддерживается. Версия
фиксируется через `packageManager` (corepack в Docker, pnpm/action-setup в CI).

### D-005. Reverse proxy: Caddy

ТЗ разрешает Caddy или Nginx. Caddy: короткий конфиг, WebSocket (Vite HMR) из коробки,
автоматический HTTPS по домену для M9 через одну переменную `SITE_ADDRESS`.

### D-006. Маршрутизация и порты

- Единая точка входа `http://localhost:${PROXY_PORT:-8080}`.
- `/api/*` → api **со снятием префикса**: `/api/v1/spin` → `api:/v1/spin`, `/api/health` → `api:/health`.
  Админские маршруты API (`/admin/*` по ТЗ 11.3) снаружи доступны как `/api/admin/*` и не
  пересекаются с SPA админки.
- `/admin/` → SPA админки (Vite `base: '/admin/'`), `/` → Mini App.
- Postgres и Redis наружу не публикуются (`make` и инструменты работают внутри сети compose).

### D-007. Проверки через Docker, CI нативно

`make lint|typecheck|test|format|build` выполняются в контейнере `tools` (профиль `tools`), поэтому
на хосте нужны только Docker и make. GitHub Actions запускает те же `pnpm`-скрипты нативно (быстрее)
и отдельно собирает prod-образы.

### D-008. Workspace-пакеты без пересборки в dev

`@spincards/shared` и `@spincards/game-core` собираются `tsc` в `dist`, но в `exports` есть условие
`@spincards/source` → `src/index.ts`. Его используют Vite, Vitest, swc-node и `tsc` (`customConditions`),
поэтому в dev правки в пакетах видны сразу. Prod-сборка (`tsconfig.build.json`) условие отключает
и берёт `dist`.

### D-009. Рантайм api в dev: swc-node

NestJS DI требует `emitDecoratorMetadata`; esbuild/tsx и oxc её не генерируют. В dev api, worker и bot
запускаются `node --watch --import @swc-node/register/esm-register`, тесты api используют `unplugin-swc`,
prod-сборка — обычный `tsc`. Всё ESM (`"type": "module"`, `NodeNext`).

### D-010. Readiness без Prisma

`GET /health` — liveness. `GET /health/ready` проверяет Redis (`PING`) и Postgres (TCP-соединение).
В M2 проверка Postgres заменяется запросом через Prisma.

### D-011. Миграции и сиды до M2

Скрипты `migrate`/`seed` в M0 — заглушки, но цепочка уже работает: entrypoint api при
`RUN_MIGRATIONS=true` (задано только у сервиса `api`, не у `worker`) выполняет их перед стартом.
Prisma (её `latest` сейчас указывает на 8.0.0-rc) выбирается в M2.

### D-012. Бот в M0

- Без `BOT_TOKEN` бот стартует в режиме idle с предупреждением в логе, health-check зелёный:
  `make up` работает на чистой машине без токена.
- Только long polling; webhook для prod делается в M6 (вместе с остальной логикой бота).
- Кнопка «Играть» (web_app) добавляется, только если `PUBLIC_URL` начинается с `https://`
  (Telegram отклоняет другие URL); иначе бот пишет, что мини-приложение пока недоступно.

### D-013. `PUBLIC_URL` в одном месте

`PUBLIC_URL` задаётся в `infra/.env` и передаётся в контейнеры через compose, чтобы при смене
адреса туннеля не править несколько файлов.

### D-014. Версии инфраструктуры

Как в ТЗ: PostgreSQL 16 (`16.15-alpine`), Redis 7 (`7.4.11-alpine`, AOF включён). Caddy `2.11.7-alpine`,
cloudflared `2026.9.3`. Все теги закреплены точно.

### D-015. i18n

- Ресурсы (`common`, `game`, `shop`, `errors`, `bot`) лежат в `packages/shared/src/i18n/locales/<lang>/`,
  общие опции `i18nOptions()` там же; web, admin и bot подключают i18next + `i18next-icu`
  (ICU plural, интерполяция `{name}`).
- Язык: `resolveLanguage()` сводит код к поддерживаемому, запасной `ru`. В M0 web берёт
  `navigator.language`; `language_code` из Telegram подключается в M4. Отдельный language-detector
  не ставим.
- Тест в `shared` гарантирует, что у каждого `ErrorCode` есть перевод.

### D-016. Название игры

Рабочее название хранится в ключе `common:appName` и нигде не захардкожено. Перенос в игровой
конфиг БД — в M2 вместе с конфигом.

### D-017. Формат ошибок и request id

- Ответ об ошибке: `{ "error": { "code": "<ErrorCode>", "requestId": "<id>" } }`, без текста и стека.
- `x-request-id`: принимается входящий, если соответствует `[A-Za-z0-9_-]{1,64}`, иначе генерируется UUID;
  возвращается в ответе и пишется в логи как `request_id`. Заголовки с токенами редактируются в логах.

### D-018. Supertest позже

В M0 HTTP-тесты api используют `fastify.inject` (без сети и лишних зависимостей).
Supertest добавим, когда понадобятся тесты поверх реального сервера (M2–M3).

### D-019. Prod-образы web/admin

Runtime-стадия web/admin — Caddy со статикой и SPA-fallback. Главный proxy переключается между dev
(Vite) и prod (статикой) через переменные `WEB_UPSTREAM`/`ADMIN_UPSTREAM`. HTTPS на домене и
доводка prod-compose для VPS — M9.

### D-020. `make sim`

До M1 команда печатает заглушку; симулятор появится в `packages/game-core`.

## M0. Доработки по обратной связи (2026-10-12)

### D-021. Туннель по умолчанию: ngrok

По решению владельца проекта `make tunnel` поднимает ngrok (профиль compose `ngrok`, образ
`ngrok/ngrok:3.39.11-alpine`). Бесплатный аккаунт ngrok даёт постоянный статический домен
(`NGROK_DOMAIN`), поэтому адрес Mini App в BotFather стабилен. Cloudflare Quick Tunnel остаётся
запасным вариантом без регистрации: `make tunnel TUNNEL=cloudflared` (профиль `cloudflared`).
Это отличается от ТЗ 16, где первым вариантом указан cloudflared; CLAUDE.md обновлён.
Vite разрешает хосты `*.ngrok-free.app|dev`, `*.ngrok.app|dev`, `*.trycloudflare.com`.

### D-022. Только pnpm

В проекте не используется npm: entrypoint api вызывает `pnpm run migrate/seed`. Поэтому
runtime-образ api собирается от стадии `base`, где pnpm установлен через corepack
(`COREPACK_HOME=/usr/local/share/corepack`, доступен пользователю `node`).

### D-023. `make restart` пересоздаёт контейнеры

`docker compose restart` не перечитывает `env_file`, из-за этого бот не видел добавленный `BOT_TOKEN`.
`make restart [s=<service>]` теперь выполняет `up -d --force-recreate --no-deps`.

## M1. game-core (2026-10-12)

### D-024. Калибровка `base_limit` под коридор RTP

Цифры ТЗ давали RTP (с комиссией 10%, без учёта Stars) примерно 61–85% у Базового, 139% у Бизнеса и
283–290% у Премиума: паттерны только повышают стоимость, поэтому Премиум не мог попасть в коридор.
Цены, шансы тиров и множители оставлены как в ТЗ; диапазоны `base_limit` платных пакетов пересчитаны
симулятором под RTP ≈ 95% (1 млн прокрутов, 200 игроков, 30% оплат картой, уровень 1):

| Пакет   | ТЗ, ₽         | Стало, ₽      | Стало, $ | RTP RU / US   |
| ------- | ------------- | ------------- | -------- | ------------- |
| Базовый | 300–900       | 340–1 010     | 4–12     | 95.5% / 94.2% |
| Бизнес  | 8 000–13 000  | 5 400–8 900   | 62–100   | 94.9% / 94.8% |
| Премиум | 60 000–90 000 | 19 700–29 600 | 218–327  | 94.8% / 95.6% |

Оплата картой даёт RTP до ~99% (бонус удачи). Бесплатный и VIP-пакет (только Stars) не калибровались:
у них нет цены в валюте. Шансы будут подгоняться при тестировании (решение владельца).

### D-025. Полный дубль только один

Первая цифра всегда `9` (жёсткое правило), поэтому из «10 полных дублей» (ТЗ 4.6) возможен только
`9999 9999 9999 9999`. Он проходит запрет Луна, принудительно Mythic, существует в единственном экземпляре.

### D-026. Потолок множителя номера для всех паттернов

Потолок ×60 применяется к сумме всегда, в том числе к лестнице длины 10 (×100) и полному дублю (×100).
Очки редкости этих паттернов начисляются полностью.

### D-027. Правила пересечения паттернов

- Множители паттернов складываются (×2.5 + ×2.0 = ×4.5); без паттернов множитель ×1.
- В блоке засчитывается один блочный паттерн (четвёрка, лестница в блоке или радар; они взаимоисключающие).
- Хвост конкурирует с паттерном последнего блока, засчитывается больший множитель (при равенстве хвост):
  `7777` это хвост ×12, а не хвост + четвёрка.
- Длинная лестница: максимальная серия шагом +1 или −1 через границы блоков, без перехода 9→0.
  Блочная лестница внутри длинной не засчитывается. Две длинные лестницы засчитываются обе; соседние
  серии могут делить «точку разворота» (`…543212345…`).

### D-028. Генерация номера и веса паттернов

ТЗ не задаёт вероятности паттернов. В конфиге у каждого паттерна есть `weight`, у отсутствия паттерна
`noPatternWeight` (по умолчанию 91.9% без целевого паттерна). Генератор выбирает цель по весам, ставит
паттерн в случайную допустимую позицию и случайно заполняет остальные цифры; естественно возникшие
паттерны тоже засчитываются (всего около 12% карт с паттерном). Бонус удачи карты повышает веса
паттернов в пределах того же потолка `boostCapBp`. Номер, прошедший Луна, перегенерируется.
После `maxAttempts` (10) неудач уникальности генерируются номера без паттерна.

### D-029. Уникальность учитывает пул

`UniquenessChecker` считает номер занятым, если он есть у любой карты, включая карты в пуле. Иначе
генератор мог бы выдать номер, который позже вернётся из пула, и у двух игроков оказался бы один номер.
Частичный уникальный индекс из ТЗ (active/expired) остаётся; в M2 при повторном дропе переиспользуется
та же строка карты.

### D-030. Целочисленная арифметика

Деньги в минимальных единицах, множители, шансы, бонусы и комиссии в базисных пунктах (10 000 = ×1 = 100%),
сроки жизни в часах. Баланс считается через `BigInt` (`floor(base × design × number / 10⁸)`), веса тиров
масштабируются ×10 000, выбор идёт `rng.int` по целой сумме весов.

### D-031. Удача

- Шкала удачи, pity и серия неудач ведутся по пакету (`user_counters`); сценарий новичка по общему числу
  прокрутов игрока.
- Порядок: база → «Счастливый» (Epic+ ×2) → бонус карты + бафы + бонус новичка (Rare+) → потолок:
  добавленный вес Rare+ не больше `boostCapBp` (+50%) от исходного веса Rare+, все прибавки сжимаются
  пропорционально → нормализация.
- Pity: в пакете на N-й прокрут без нужного тира выбирается тир не ниже порога (из эффективных весов).
  Сработавший порог старше сценария новичка, только если требует более высокого тира.
- Бафы влияют только на тиры, бонус карты на тиры и паттерны.
- Серия неудач сравнивает баланс выпавшей карты с ценой пакета; бесплатный пакет её не двигает.
- Возвращение: api проверяет `isReturningPlayer` (пауза ≥ 72 ч) и ставит флаг, который тратит ближайший
  бесплатный прокрут.

### D-032. Near-miss

Подсказка = паттерн из списка `nearMiss.patternIds`, который появился бы при замене одной цифры
(кроме ведущей 9), покрывает эту цифру и которого у номера ещё нет; выбирается самый ценный. Считается
перебором по уже выпавшему номеру и на генерацию не влияет. По умолчанию в списке четвёрки, длинные
лестницы, хвосты и полный дубль; частота около 20% прокрутов (в основном «три из четырёх»). Флаг
`near_miss_ux` управляет только показом.

### D-033. Модель симулятора

N прокрутов раздаются по кругу P виртуальным игрокам (свои счётчики). Игрок держит одну карту для оплаты
и платит ею с заданной вероятностью, если хватает баланса; остальные карты сразу уходят в пул (оттуда
повторные дропы). RTP = стоимость немедленного обналичивания всех выпавших карт / сумма цен.
CLI: `make sim ARGS="--pack basic --spins 1000000 --players 200 --region US --card-share 30 --seed 42 --json"`,
`--config file.json` проверяет конфиг-кандидат. Код выхода 1, если платный пакет вне коридора.

### D-034. Открытый вопрос: фактические шансы против опубликованных

Гарантии, шкала удачи и сценарий новичка заметно поднимают фактическую долю редких тиров в дешёвых
пакетах: Базовый Rare 16.2% при опубликованных 12%, Epic 4.8% при 2.8% (Бесплатный: 15.1% / 3.9% при
10% / 1.8%). Экран «Шансы» должен честно это отражать: публиковать базовые шансы вместе с описанием
гарантий или эффективные шансы из симуляции. Решить до M5.

## M2. БД, вход, кошельки (2026-10-12)

### D-035. Prisma 7.10 с драйвером pg

`latest` у Prisma указывает на 8.0.0-rc, поэтому взята стабильная 7.10.0. Prisma 7 работает только через
driver adapter: `@prisma/adapter-pg`. Клиент генерируется в `apps/api/src/generated` (в `.gitignore`,
`postinstall: prisma generate`). Пакет `prisma` в `dependencies`: в prod-образе нужен `migrate deploy`;
в образ api попадают `dist`, `prisma/` и `prisma.config.ts`.

### D-036. Типы данных

Деньги в БД `BIGINT` (Mythic-карта Премиума может превысить предел INT), в API целые числа в минимальных
единицах (`toApiMoney` проверяет безопасный диапазон). Первичные ключи UUID v7, у `ledger_entries`,
`events`, `audit_log` автоинкремент `BIGINT` (порядок записей). Время `timestamptz(3)`.

### D-037. Ограничения в SQL миграции

Prisma не умеет: частичный уникальный индекс `cards(number) WHERE status IN ('active','expired')`
(ТЗ 4.9; проверка с учётом пула в коде, D-029), не больше одной активной версии конфига, CHECK
(номер `^9\d{15}$`, балансы ≥ 0, `delta ≠ 0`, корректные суммы конвертации и курсы), триггеры:
`ledger_entries` только INSERT (UPDATE/DELETE/TRUNCATE запрещены), из `spins` и `payments` нельзя удалять.

### D-038. Блокировки ledger

`LedgerService.lock` берёт `SELECT … FOR UPDATE` сначала по кошелькам, потом по картам, каждую группу
по возрастанию id: параллельные операции не могут взаимно заблокироваться. Транзакции READ COMMITTED;
сериализацию по счёту дают блокировки строк. Каждая запись хранит `balance_after`; промежуточный
баланс внутри пакета проводок тоже не может уйти в минус. Сверка: `make ledger-verify`.

### D-039. Идемпотентность

Таблица `idempotency_keys (user_id, key)`. Ключ вставляется в той же транзакции, что и операция:
параллельный дубль ждёт на уникальном индексе и получает сохранённый ответ. Тот же ключ с другим телом
или маршрутом даёт `422 IDEMPOTENCY_KEY_REUSED`. Неуспешная операция откатывает и ключ, повтор
с тем же ключом выполнится заново. Сохранённый ответ лежит в jsonb, поэтому порядок ключей в повторном
ответе может отличаться (содержимое то же).

### D-040. Вход и токены

- `initData` проверяется по алгоритму Telegram (HMAC, `WebAppData`), срок `INIT_DATA_MAX_AGE_SEC` ≤ 24 ч.
- Access JWT HS256 на 1 час (`jose`), refresh непрозрачный, в БД только SHA-256, живёт 30 дней,
  ротируется при каждом использовании; предъявление уже использованного токена отзывает всю цепочку.
- `POST /v1/auth/dev` регистрируется, только если `NODE_ENV=development` и `DEV_AUTH_BYPASS=true`.
- При входе после паузы ≥ 72 ч ставится `return_lucky_pending` (бонус возвращения из ТЗ 5.5).
- Бан проверяется на каждом запросе.

### D-041. Токен бота в api

api проверяет подписи `initData` тем же токеном, что использует бот: `TELEGRAM_BOT_TOKEN` в `apps/api/.env`
(в production обязателен, иначе api не стартует). Один токен хранится в двух `.env` осознанно: бот
и api разные сервисы со своими секретами.

### D-042. Rate limit

Фиксированное окно 60 с в Redis, ключ по пользователю (валидный access-токен) или по IP, группы
`default` / `auth` / `mutation` с лимитами из env. При недоступности Redis запросы пропускаются
(с записью в лог): доступность важнее троттлинга.

### D-043. Конвертация

Курс и комиссия в `exchange_rates` (ТЗ 12), курс хранится как `rate_nano` (единиц целевой валюты за 1
единицу исходной × 10⁹). Минимальная сумма, минимальная комиссия и дневной лимит в игровом конфиге.
Комиссия в исходной валюте: `max(minFee, ceil(amount × fee))`, результат округляется вниз. Дневной лимит
считается по UTC-суткам и проверяется после блокировки исходного кошелька. Проводки `convert_out` и
`convert_in`, запись в `currency_conversions`.

### D-044. Конфиг: новые разделы

`startingBalance` (5 000 ₽), `conversion`, `levels` (20 уровней; пороги EXP по умолчанию 0, 100, 250, 450,
700, 1000, 1400, 1900, 2500, 3200, 4000, 5000, 6200, 7600, 9200, 11 000, 13 000, 15 500, 18 500, 22 000;
в ТЗ их нет), `holders` (ТЗ 5.4). Новые причины ledger: `signup_bonus`, `chest`, `stars_refund`.
Счётчики уровня игрока (`total_spins`, `return_lucky_pending`) лежат в `users`, по пакету в `user_counters`.

### D-045. Публичный конфиг

`GET /v1/config/public` отдаёт опубликованные базовые шансы пакетов, гарантии, цены, холдеры, уровни,
курсы. Пакеты только за Stars и цены в Stars скрыты, пока выключен `stars_enabled`. Внутренние параметры
(веса паттернов, шанс повторного дропа) не публикуются. Как показывать фактические шансы — D-034.

### D-046. Тесты с настоящей БД

Интеграционные тесты api работают с базой `spincards_test`: globalSetup создаёт её, делает
`prisma migrate reset` и запускает сиды теми же командами, что и при старте api. Все Node-проекты тестов
компилируются SWC (одинаковая трансформация, корректное слияние покрытия). `make test` поднимает postgres
и redis; в CI они запускаются как service-контейнеры.

### D-047. Синхронизация `.env`

`make env` (вызывается из `make up`) создаёт отсутствующие `.env`, дописывает ключи, добавленные
в `.env.example` позже, и заменяет заглушку `__generate__` случайным секретом (`JWT_SECRET`).
Существующие значения не меняются.

### D-048. Админ-владелец

Сид создаёт owner из `ADMIN_OWNER_LOGIN`/`ADMIN_OWNER_PASSWORD`, пароль хешируется scrypt (`node:crypto`,
без зависимостей). TOTP и вход в админку в M8.

## M3. API игры (2026-10-12)

### D-049. Решение по выпавшей карте обязательно

Пока выпавшая карта не обналичена и не положена в холдер (`cards.held_at IS NULL`), новый прокрут
отклоняется `CARD_DECISION_PENDING`. Иначе слоты холдера обходились бы отказом от решения. Ожидающая
карта не занимает слот, но её срок жизни идёт; после сгорания блокировка снимается сама.

### D-050. Продление и восстановление

Оплачиваются с баланса самой карты (ТЗ не уточняет источник). Продление: только активная карта до
истечения, `maxExtends` раз (1), +50% исходного срока тира за 10% баланса. Восстановление: только в
льготное окно, за 25% баланса, срок начинается заново на полный срок тира.

### D-051. Обналичивание сразу в пул

Обналиченная карта получает статус `pooled` (без владельца, баланс 0) в той же транзакции; статус
`cashed` из ТЗ не используется, так как операция атомарна. Комиссия по уровню, у просроченной карты
штрафная 20%.

### D-052. Эмиссия и сток через ledger

Баланс выпавшей карты зачисляется проводкой `card_issue`, сгорание по сроку проводкой `card_burn`. Так
баланс любой карты восстановим из ledger, а эмиссия и сток видны в аналитике (M7).

### D-053. EXP и награды уровней

EXP за прокрут по пакету (Бесплатный 1, Базовый 10, Бизнес 60, Премиум 200), бонус за тир
(Rare 2, Epic 10, Legendary 30, Mythic 100), 20 за ежедневный вход. Уровень пересчитывается сразу.
Награды уровня в M3: снижение комиссии обналичивания и открытие пакетов (`unlockLevel`: Бизнес 3,
Премиум 8) и холдеров. Слоты и бафы за уровень ТЗ не описывает, не реализованы.

### D-054. Ежедневная серия

Сутки по UTC. Награды по умолчанию: 1) 500 ₽ / $6, 2) баф +5% на 3 прокрута, 3) 1 000 ₽ / $12, 4) бесплатный прокрут, 5) 1 500 ₽ / $17, 6) баф +10% на 3 прокрута, 7) 3 000 ₽ / $34 и гарантированный
Epic+ на следующий прокрут любого пакета. Деньги зачисляются на кошелёк текущего региона. Пропуск ровно
одного дня прощается раз в 7 дней, иначе серия начинается заново; после 7-го дня снова день 1.
Запрос идемпотентен по `idempotencyKey`, второй вход за сутки даёт `DAILY_ALREADY_CLAIMED`.

### D-055. Бесплатные прокруты

Новый игрок получает полный запас (3). Начисление ленивое: хранится запас и начало текущего интервала,
при чтении досчитывается по времени. Бонусные прокруты (награда серии) могут превышать потолок; пока
запас выше потолка, начисление стоит.

### D-056. Порядок блокировок

Каждая мутация игрока сначала блокирует строку `users` (`FOR UPDATE`): действия одного игрока
выполняются по очереди, а дальше блокировки идут в одном порядке (игрок → кошельки → карты). Пул
берётся `FOR UPDATE SKIP LOCKED` (самая давняя карта первой), джоба сгорания тоже `SKIP LOCKED`.

### D-057. Никаких запросов к общему пулу внутри транзакции

Нагрузочный тест нашёл голодание пула: внутри транзакции обновлялся кэш конфига и флагов через общий
клиент, и при 10 соединениях все транзакции ждали друг друга до таймаута (11 rps, p99 60 с). Теперь
конфиг, сезон и флаги загружаются до открытия транзакции, а внутри используется только `tx`.
Размер пула `DATABASE_POOL_SIZE` (по умолчанию 20).

### D-058. Эффективный статус карты

Джоба сроков запускается раз в минуту. До её прохода карта с истёкшим сроком считается просроченной
(штрафная комиссия, можно восстановить), а с истёкшим льготным окном считается сгоревшей.

### D-059. Обновление схемы конфига

Если активная версия конфига не проходит новую схему, сид дополняет недостающие ключи значениями
по умолчанию (массивы с `id` сливаются по id, настроенные значения сохраняются) и делает результат
новой активной версией; старая архивируется. Прокруты продолжают ссылаться на версию, с которой
были сделаны.

### D-060. Worker

Worker поднимает Nest application context (Prisma, ledger, конфиг) без HTTP. BullMQ job scheduler
`card-lifecycle` раз в 60 секунд: одно расписание при любом числе worker'ов, concurrency 1.

### D-061. Нагрузочный тест `/spin`

`make load-spin` поднимает отдельный экземпляр api на `spincards_test` с поднятыми лимитами, создаёт
игроков, пополняет их через ledger и гоняет циклы «прокрут → обналичить» по HTTP. Результат на машине
разработки (50 игроков, 30 с): 213 прокрутов/с, p50 126 мс, p95 162 мс, p99 224 мс, ошибок 0,
расхождений ledger 0, дубликатов живых номеров 0.

### D-062. Перенесено из M3

Сундучок, магазин бафов и награды рефералам (маршруты есть в ТЗ 11.1, но не в критериях M3)
предлагается сделать вместе с экранами в M5.

## Нагрузка (2026-10-13)

### D-063. Цель по нагрузке и перенос оптимизации в M9

Цель ≥ 1000 прокрутов/с при p95 ≤ 300 мс. Сейчас ~220/с, предел — один процесс Node. Владелец проекта
решил отложить оптимизацию до M9; замеры и план в `docs/performance.md`.

## M4. Frontend: основа (2026-10-13)

### D-064. Общие типы API

Формы ответов REST (`MeResponse`, `CardView`, `SpinResponse`, `PublicConfigResponse` и др.) перенесены
в `@spincards/shared/api` (правило CLAUDE.md «общие типы только из shared»); api и web используют одни
и те же типы. В публичный конфиг добавлены банки (названия из БД) и параметры бесплатных прокрутов.

### D-065. Стек Mini App

`@telegram-apps/sdk-react` 3 (по ТЗ), TanStack Query 5 (данные сервера), Zustand 5 (сессия, навигация,
тосты), `motion` 14 (так теперь называется Framer Motion, API тот же). Роутер не используется: экранов
мало, собственный стек экранов связан с кнопкой «Назад» Telegram. Экраны грузятся лениво. Тесты
компонентов: Testing Library + jsdom.

### D-066. Вход на клиенте

Токены только в памяти, при каждом запуске вход заново по `initData` (живёт 24 ч). На 401 клиент один
раз обновляет токен через refresh, при неудаче входит заново. В обычном браузере вход через
`/v1/auth/dev`, только если `VITE_DEV_AUTH=true` в web и `DEV_AUTH_BYPASS=true` в api (development).
Мок-id для dev-входа хранится в `localStorage` (не секрет).

### D-067. Мутации с клиента

Ключ идемпотентности создаётся один раз на действие игрока (UUID v4 через `crypto.getRandomValues`:
`crypto.randomUUID` недоступен вне HTTPS на dev-хостах). При обрыве сети запрос повторяется до двух раз
с тем же ключом. Балансы в кэше меняются только данными из ответов сервера, оптимистичных обновлений нет.

### D-068. Честная лента

Результат приходит с сервера до анимации, лента только едет к нему. Заполнители — безымянные рубашки
(цвет банка, без тира и номера), поэтому лента не может изобразить «почти» рядом с редкой картой. При
near-miss последние кадры замедляются (ТЗ 4.8). Анимация пропускается тапом и выключается при
`prefers-reduced-motion`.

### D-069. Дизайн карты

Только собственный CSS/SVG: палитра, узор и знак банка, материал тира поверх, чип, номер с подсветкой
паттернов (длинные лестницы подчёркнуты цепочкой), имя игрока из Telegram заглавными, «N-й владелец»,
пометка «игровая карта». Цвет текста и подсветки тира важнее цвета банка (например, светлый текст на
Mythic у жёлтого банка, тёмный на платине Legendary). Срок показан как «до ДД.ММ»: карты живут дни,
привычное «ММ/ГГ» было бы у всех одинаковым. Наклон карты от касания; гироскоп в M5.

### D-070. Карта без решения

Если приложение закрыли до решения по выпавшей карте, при запуске экран открывается на ней (сервер
всё равно не даст крутить дальше). После «Обналичить»/«В холдер» карта не всплывает повторно, пока
кэш холдера обновляется.

### D-071. Бюджет бандла и галерея

`pnpm --filter @spincards/web build` падает, если JS+CSS больше 500 КБ gzip (сейчас ~209 КБ).
Dev-сборка показывает галерею всех карт по адресу `/#gallery` для оценки дизайна; в prod её нет.

## M5. Frontend: остальное (2026-10-13)

### D-072. Сундучок

Сундучок за каждые 10 прокрутов (`chest.everySpins`), неоткрытых хранится не больше 3 (`maxStored`),
сверх потолка сгорают при открытии. Награды по умолчанию (веса 50/30/20): 300 ₽ / $3.5, 800 ₽ / $9 или
баф +5% на 3 прокрута. Деньги на кошелёк текущего региона (проводка `chest`), открытие идемпотентно.

### D-073. Магазин

Магазин за валюту (ТЗ 8): малый/средний/большой баф удачи (+5% на 5, +10% на 5, +20% на 10 прокрутов:
500 ₽, 1 500 ₽, 5 000 ₽) и 3 бесплатных прокрута за 1 500 ₽. Холдеры покупаются на экране холдера,
продление и восстановление на экране карты. Цены в конфиге; влияние бафов на экономику проверим
симулятором при подгонке шансов.

### D-074. Награды рефералам автоматически

Когда приглашённый сделал 5 прокрутов и достиг 2-го уровня, оба получают награду (1 000 ₽ / $12
пригласившему, 500 ₽ / $6 приглашённому, в валюте текущего региона каждого) в той же транзакции прокрута
или ежедневной награды. Дневной лимит 10 награждённых на пригласившего; сверх лимита реферал ждёт
следующего действия. Маршрут `POST /v1/referrals/claim` из ТЗ не нужен: награда приходит сама.

### D-075. Рейтинги до M7

`GET /v1/leaderboard` считает рейтинг запросом к БД: по балансу — сумма кошельков в рублях по текущему
курсу (стоимость карт не учитывается), по коллекции — сумма редкости живых карт. Скрытые и забаненные
игроки не показываются, одинаковые очки делят место. В M7 переезжает на Redis sorted sets со снимками.

### D-076. Публичный конфиг для экранов

Добавлены множители и очки паттернов, параметры продления/восстановления, награды серии и сундучка,
товары магазина, условия рефералов, купленные холдеры в `/v1/cards`. Клиент показывает превью
(комиссия обмена, цена продления) по тем же формулам, что и сервер, но решение всегда за сервером.
Веса генерации паттернов и шансы наград сундучка не публикуются.

### D-077. Навигация и экраны

Пять вкладок (Игра, Холдер, Кошелёк, Бонусы, Рейтинг) и общая шапка; профиль (по аватару), карта,
«Шансы», правила и конфиденциальность открываются поверх вкладок и закрываются кнопкой «Назад»
Telegram. Онбординг из 3 экранов показывается игроку без прокрутов один раз (отметка в `localStorage`).
Тексты правил и политики конфиденциальности (ТЗ 19) в i18n.

### D-078. Холдер и карта

Холдер показывает все карты (в том числе с маленьким балансом и просроченные с таймером сгорания),
веер из пяти самых редких, слоты и покупку холдеров. Экран карты: наклон гироскопом (на iOS по кнопке
с запросом разрешения) или касанием, пополнение с кошелька, продление, восстановление, обналичивание
с подтверждением.

### D-079. Реферальная ссылка

`https://t.me/<бот>?startapp=ref_<код>`, имя бота API узнаёт через `getMe` и отдаёт в публичном конфиге (`botUsername`, M9); «Поделиться» открывает
`t.me/share/url` средствами Telegram.

## Правки после тестирования (2026-10-13)

### D-080. Мультипрокрут ×1–×4

`POST /v1/spin {count}`: одна оплата N × цена (кошелёк, карта или N бесплатных) и N прокрутов подряд в
одной транзакции; счётчики, гарантии, бафы и сценарий новичка идут от прокрута к прокруту как при
отдельных прокрутах. Ответ: `spins[]`. Все N карт ждут решения; новый прокрут после решения по всем.
На экране N лент одновременно, каждая останавливается на своей реальной карте.

### D-081. Обналичивание на карту

`POST /v1/cards/:id/cashout {toCardId}`: выплата (та же комиссия) уходит на другую карту игрока той же
валюты в холдере, активную и не просроченную. Если прокрут оплачен картой, это главная кнопка
результата.

### D-082. Бафы магазина под пакет

Баф покупается для конкретного платного пакета: цена = цена пакета × прокруты × `pricePerSpinBp`.
Симулятор показал, что +5/+10/+20% к Rare+ дают до 0,9/1,7/3,2% цены пакета на прокрут (максимум на
Бизнесе, на Премиуме почти 0); цены 1,5/2,5/5% за прокрут, чтобы баф не был выгоден в среднем ни на одном
пакете. Один активный баф магазина на пакет (`BUFF_ALREADY_ACTIVE`), не больше 3 покупок бафов в сутки.
Бафы серии, сундучка и колеса действуют на любой пакет; всё вместе ограничено общим потолком +50%.

### D-083. Уровни сундучка, колесо, рост наград

- Сундучок: 5 уровней, улучшение за валюту (50 тыс., 200 тыс., 800 тыс., 3 млн ₽; Stars позже за флагом);
  у каждого уровня своя таблица наград (деньги, бафы, бесплатные прокруты, гарантия Rare+/Epic+),
  шансы публикуются на экране «Шансы».
- Колесо фортуны: бесплатно раз в 4 часа, 8 секторов (деньги, бафы, бесплатные прокруты, джекпот), сектор
  выбирает сервер до анимации, шансы публикуются. Проводка `wheel`.
- Денежные награды серии, сундучка и колеса растут на 15% за уровень игрока (`rewardLevelBonusBp`).
- Серия: деньги, баф, 2 бесплатных прокрута, деньги ×2, Rare+, деньги ×3 и баф, на 7-й день Epic+,
  деньги ×5 и сундучок.
- Бесплатный пакет: `base_limit` +3% за уровень игрока (`levelBaseLimitBonusBp`), шансы тиров не меняются.

### D-084. Рейтинг по балансу с картами

По решению владельца баланс в рейтинге = кошельки + балансы живых карт (в рублях по текущему курсу).
Это отличается от ТЗ 7.3, где стоимость карт не учитывалась.

### D-085. Уровень коллекции

Очки коллекции = сумма редкости карт в холдере, уровень по порогам `collectionLevels` (0, 25, 75, 150,
300, 600, 1200, 2500), показывается в холдере.

### D-086. Несовместимое изменение схемы конфига

Если после дополнения недостающих ключей активная версия всё равно не проходит схему (например, список
превратился в уровни), сид создаёт новую версию из значений по умолчанию с пометкой в комментарии.
В prod такие изменения конфига требуют ручного переноса настроенных значений.

### D-087. Раскладка экрана рулетки

Высота по стабильной высоте viewport Telegram, строка с кнопкой «Выпустить» закреплена и не двигается;
ленты и результат открываются слоем над ней, остальная панель прячется, сохраняя место (без дёрганья).
Пропуск ленты тапом в любом месте. В холдере и веере карты статичные (без анимаций и смешивания слоёв).
Выбор пакета, оплаты и числа прокрутов хранится локально и переживает смену вкладок.

### D-088. Переводы между кошельком и картами

`POST /v1/transfers {from, to, amount}`: кошелёк→карта без комиссии, карта→карта 1%
(`transfer.cardToCardFeeBp`), карта→кошелёк по комиссии обнала уровня игрока (по решению владельца),
карта остаётся в холдере. Иначе перевод в кошелёк стал бы обналом без комиссии и обходил бы RTP.
Комиссия округляется вверх и списывается из суммы перевода; только активные карты из холдера в одной
валюте; проводка `transfer`. Комиссия обнала уровня отдаётся в `/v1/me` (`game.cashoutFeeBp`), чтобы
показать её до подтверждения.

### D-089. Решения по нескольким картам одним запросом

«Всё в кошелёк / на карту / в холдер» идут одним запросом (`/v1/cards/cashout-many`,
`/v1/cards/hold-many`, до 4 карт): всё или ничего, одна транзакция и один ключ идемпотентности.
На клиенте решённые карты запоминаются до конца сессии экрана, поэтому устаревший ответ холдера
не возвращает их на экран; пока идёт прокрут, оставшиеся карты из холдера не показываются.

### D-090. Лента и экран результата

Лента — 16 лёгких карточек (без компонента карты, теней, масок и узоров), края затемняются наложенными
градиентами. Номера пролетающих карт размыты и не настоящие, тир на них не показывается; номер
выпавшей карты проявляется при остановке. Экран результата не прокручивается: карты подбираются по
размеру свободного места (container queries), значки, «Почти…» и кнопки — в подвале, прижатом к низу,
поэтому кнопки решений стоят на одном уровне при любом числе карт.

### D-091. Новые ключи конфига читаются со значениями по умолчанию

Если активная версия конфига в БД не содержит ключ, добавленный новым релизом, api при чтении
подставляет значение по умолчанию (то же дополнение, что делает сид). Так выкатка не ломается
до запуска `make seed`; сид по-прежнему сохраняет дополненную версию в БД.

### D-092. Правила уведомлений бота

Числа в конфиге (`notifications`): тихие часы 23:00–09:00 по часовому поясу региона
(RU — Europe/Moscow, US — America/New_York), не больше 3 игровых уведомлений в сутки по местному
времени, предупреждение о сгорании за 6 часов до конца срока (только карты в холдере), напоминание
о возвращении после 72 часов без входа (одно на каждый перерыв), до 5 попыток отправки,
25 сообщений в секунду. Награда реферала приходит пригласившему. Правила проверяются в момент
отправки: отложенное ночью сообщение утром проверяется снова, устаревшее (карта уже обналичена,
игрок вернулся) не отправляется, сверх лимита — пропускается, а не переносится. Рассылки
в суточный лимит не входят, но учитывают выключенные уведомления, блокировку и тихие часы.
Одно событие — одно сообщение (уникальный ключ события в outbox).

### D-093. Внутренний API бота

`/internal/bot/*` защищён общим секретом в заголовке `x-internal-token` (сравнение за постоянное
время), отдельный лимит запросов, proxy отвечает 404 на `/api/internal*`. Бот регистрирует игрока
по `/start` тем же путём, что и Mini App (реферальный параметр учитывается только у нового игрока),
`/start` снимает отметку о блокировке. Бот забирает уведомления пачкой с арендой на 5 минут:
если он упадёт посреди отправки, сообщения уйдут повторно после аренды.

### D-094. Оплата Stars (заготовка)

Работает только при `stars_enabled`. Товары `star_products` видов `currency_bundle` (валюта региона
игрока), `buff`, `free_spins`, `holder`; вид `pack` (платный прокрут) не поддержан до отдельного
этапа платежей. Платёж начисляется через ledger (`stars_purchase`) один раз на
`telegram_payment_charge_id`, даже если флаг выключили после оплаты. Возврат (`refundStarPayment`)
делается из админки в M8. Интерфейса покупки в Mini App пока нет.

### D-095. Рассылки до админки

Сервис рассылок готов (сегменты «все / активные / неактивные N дней», запись в `audit_log`);
до админки (M8) рассылка запускается командой `make broadcast`.

### D-096. Рейтинги в Redis

Отдельный sorted set на каждый сезон и тип (`lb:<сезон>:balance|collection`). Баланс считается с картами
(D-084), коллекция — по живым картам. Worker раз в 10 секунд пересчитывает игроков, у которых после
прошлой синхронизации появились записи ledger или изменились карты (с запасом в минуту на поздние
коммиты), раз в час пересобирает рейтинги целиком (это же учитывает смену курса и баны) и при пустом
Redis строит их заново. Скрытие из рейтинга применяется сразу. Если Redis недоступен или рейтинг ещё
не построен, экран считается SQL-запросом. Одинаковые очки дают одинаковое место.

### D-097. События и активность

В `events` пишутся только сигналы, которых нет в других таблицах: `signup`, `app_open` (из Mini App),
`spin` (тир, паттерны, near-miss, выданный баланс, цена, источник карты), `card_held`, `bot_start`,
`bot_blocked`, `bot_unblocked`. Траты, выплаты, конвертации, платежи и уведомления считаются из своих
таблиц. События пишутся в транзакции действия. Активный день игрока — день, когда он открыл
приложение или крутил. Сессия — `app_open` больше чем через 30 минут после предыдущего.

### D-098. Ежедневные метрики

Сутки — календарный день по Москве (`analytics.timezone` в конфиге). Задача раз в час пересчитывает
сегодня, вчера и когорты за 31 день, заменяя строки дня. Балансы (средний, медиана, доля топ-1%),
размер пула и очередь уведомлений — снимок на момент расчёта, пишутся только за текущий день.
Фактический RTP пакета — выданные балансы карт к цене платных прокрутов. Эмиссия и сжигание — сумма
положительных и отрицательных чистых потоков ledger по причинам за день. Retention D1/D7/D30 и
воронка хранятся под датой регистрации когорты. До админки метрики смотрятся `make stats`.

### D-099. Хранение снимков рейтинга

Каждые 5 минут сохраняется топ-100 каждого типа. Через 7 дней остаётся только снимок 00:00–00:05 UTC
каждого дня.

### D-100. Возврат Stars

Возврат делает только владелец, с причиной. Сначала забирается товар: деньги — обратными проводками
`stars_refund` ровно по проводкам покупки (баланс не может уйти в минус), баф обнуляется, бесплатные
прокруты списываются, холдер снимается, если хранящиеся карты помещаются в оставшиеся слоты. Если
игрок уже потратил товар, возврат отклоняется (`PAYMENT_NOT_REFUNDABLE`): сначала ручная корректировка,
потом возврат. Затем вызывается `refundStarPayment`; если Telegram отказал, вся операция откатывается.

### D-101. Вход в админку и роли

Логин и пароль (scrypt) плюс TOTP (RFC 6238, 30 секунд, 6 цифр). При первом входе секрет показывается
один раз и сохраняется зашифрованным (AES-256-GCM, ключ `ADMIN_SECRET_KEY`, обязателен в production);
код нельзя использовать повторно. Пять ошибок подряд блокируют логин на 15 минут. Сессия — случайный
токен в httpOnly-cookie (SameSite=Strict), в БД хранится только его хеш; срок 12 часов, выход по
простою через 60 минут. Изменяющие запросы требуют заголовок `x-admin-request` (защита от CSRF).
Роли: владелец — всё; поддержка — игроки (без изменения балансов), рассылки, пул, платежи (просмотр),
сезоны; аналитик — пул, флаги и сезоны на чтение (метрики и конфиги — в M8b). Маршрут без явных ролей
доступен только владельцу. Входы, выходы, ошибки входа и все изменения пишутся в audit_log.

### D-102. Версии конфига в админке

Новая версия — черновик из активной; правка через JSON (весь конфиг) и форму пакетов (включение,
уровень, цены, веса тиров), проверка по схеме, отличия от активной по параметрам. Симуляция гоняет
каждый включённый платный пакет в каждом регионе, где он продаётся (по умолчанию 50 000 прокрутов на
пакет, seed 42), и сохраняет отчёт. Активировать можно только версию, у которой все пакеты в коридоре
RTP; правка после симуляции возвращает её в черновик. Откат — повторная активация архивной версии.
Создание, правка, симуляция и активация — только владелец; аналитик смотрит.

### D-103. Предохранители

Раз в 5 минут worker считает фактический RTP платных пакетов за последний час по событиям прокрутов.
Выход за [50%, 150%] при 500+ прокрутах — алерт в журнал; превышение верхней границы ставит пакет на
паузу (флаг `pack_paused:<пакет>`: прокрут отклоняется, пакет скрыт в Mini App), снимает паузу
владелец в разделе «Флаги». Дневная эмиссия выше лимита (RUB 100 млн ₽, USD 1,1 млн $) — алерт без
остановки игры. Повторный алерт по тому же поводу не чаще раза в окно. Все пороги в конфиге
(`safeguards`).

### D-104. Заготовка A/B

Группа эксперимента (`experiment_group` игрока) привязывается к версии конфига, прошедшей симуляцию.
Версия группы применяется только к прокрутам (шансы, цены пакетов); остальная экономика берётся из
активной версии. Игрок попадает в группу вручную из карточки игрока (владелец).

### D-105. Недоступные чаты и выборочная доставка

Если Telegram отвечает «chat not found» (игрок ни разу не запускал бота, например тестовые
dev-аккаунты), игрок помечается недоступным так же, как при блокировке, и выпадает из рассылок до
`/start`. `NOTIFY_KINDS` в `apps/bot/.env` ограничивает доставку видами уведомлений; в dev включены
только рассылки (`NOTIFY_KINDS=broadcast`), игровые уведомления ждут в очереди.

### D-106. 300 уровней

Опыт для уровня n = 127,5 · (n − 1)^1,72 (с округлением до десятков): каждый следующий уровень дороже,
активный игрок (около 75 тыс. EXP в день, как у тестеров) доходит до 300-го примерно за месяц.
Бонусы за уровень растянуты на 300 уровней: денежные награды +1% за уровень (было +15%, к 300-му было
бы ×46), снижение комиссии обнала 0,03% за уровень до минимума 2% к 268-му, бесплатный пакет +0,3%
к лимиту за уровень, холдеры открываются с 10, 50 и 120 уровня. Пакеты по-прежнему с 3 и 8 уровня.
Уровни игроков пересчитываются из накопленного EXP при следующем прокруте.

### D-107. Сундучок и удача

Сундучок раз в 30 прокрутов (было 10), награды примерно втрое больше, на высших уровнях сундучка —
бесплатные прокруты и гарантия Epic или Legendary. Счастливый прокрут: шкала удачи 30 (по решению владельца
оставлена прежней), Epic+ ×3 (было ×2) и гарантия не ниже Rare. Каждый 500-й прокрут игрока — особый счастливый прокрут
с гарантией Epic+ (`luck.milestone`), шкала удачи на нём не тратится. Удача карты от редкости номера:
+2% за очко редкости, до +20% (было +1%, до +10%). Симулятор: RTP платных пакетов 92–102%.

### D-108. Рефералы: процент с прокрутов друга

Приглашённый получает 5 000 ₽ (55 $), когда сделает 5 прокрутов и достигнет 2 уровня. Пригласивший
вместо разовой суммы получает 5% от стоимости платных прокрутов друга за первые 30 дней (в валюте
прокрута; начисляет worker раз в 10 минут, проводка `referral`), в профиле видно, сколько заработано
с каждого друга. Числа в конфиге (`referral.commission`).

### D-109. Лимит эмиссии считается по чистой эмиссии

Карта, выпущенная за прокрут, оплачена ценой прокрута, поэтому валовая эмиссия (сумма всех
зачислений) в десятки раз больше реально новых денег. Предохранитель сравнивает с лимитом чистую
эмиссию за день: все зачисления минус все списания по валюте.

### D-110. Обязательная подписка на канал

Владелец в админке («Настройки») включает проверку и задаёт до 5 каналов (@username или -100…,
название, ссылка). Пока проверка включена, игровые маршруты отвечают `SUBSCRIPTION_REQUIRED`, Mini App
показывает экран подписки, бот на `/start` присылает кнопки каналов и «Я подписался». Профиль,
публичный конфиг и сама проверка работают без подписки. Статус берётся из Telegram (`getChatMember`,
бот должен быть администратором канала) и кэшируется: подписан — 10 минут, не подписан — 30 секунд,
«Я подписался» проверяет заново. Если Telegram не отвечает или бот не админ канала, игрока пускают
(ошибка настройки не должна закрыть игру всем); кнопка «Проверить бота» в админке показывает такие
проблемы. Сам бот (токен) меняется только через `.env`.

### D-111. Понятная админка

Основные параметры конфига (удача, бонусы, комиссии, рефералы, предохранители) правятся формой с
русскими названиями, подсказками и единицами (%, ×, ₽/$); пакеты — таблицей с ценами в рублях и
долларах и долей каждого тира в процентах; всё остальное — в JSON. Алерты предохранителей объясняют,
что произошло и что делать, ведут в нужный раздел и скрываются кнопкой (в этом браузере). У каждого
раздела есть короткое описание. Баланс карты игрока владелец меняет так же, как кошелёк: через ledger,
с причиной, не ниже нуля.

### D-112. Сундучки считаются в прокрутах

Раньше хранилось число открытых сундучков, а доступные считались как прокруты / период − открытые.
После смены периода с 10 на 30 прокрутов у активных игроков открытых оказалось больше, чем положено
по новым правилам, и сундучки перестали начисляться. Теперь хранится, сколько прокрутов уже
превращено в сундучки (`chest_spins_used`): доступно (прокруты − использованные) / период, не больше
запаса. Смена периода в конфиге больше ничего не ломает. При миграции каждый ранее открытый сундучок
засчитан как 10 прокрутов (период, по которому его открыли).

### D-113. Ежедневные награды растут с уровнем

У ежедневной награды свой рост: деньги +4% за уровень выше первого (к 26-му ×2, к 100-му ×5, к 300-му
×13), каждые 25 уровней бесплатных прокрутов и прокрутов бафа становится на один больше. Гарантии и
сундучок не меняются. Формула общая для сервера и Mini App (`scaleDailyReward`), числа в конфиге
(`daily.levelBonusBp`, `daily.levelStep`). Остальные денежные награды растут как раньше (+1% за уровень).

### D-114. Просмотр карты, «Поделиться» и «Сохранить»

Нажатие на выпавшую карту открывает её крупно: «Прокрутить» (карта делает оборот), «Поделиться»,
«Сохранить». Картинку рисует Mini App (canvas, JPEG ~70 КБ: цвета банка, номер, баланс, тир, «игровая
карта», SpinCards) и загружает её на сервер. Там она хранится час по случайной ссылке, которую может
открыть Telegram. «Поделиться» сохраняет подготовленное сообщение с фото (`savePreparedInlineMessage`)
и открывает выбор чата (`shareMessage`). Подпись: «Мне выпала … карта •••• NNNN в SpinCards! Испытай
удачу: <реферальная ссылка>» и строка канала из админки («Настройки → Подпись при отправке карты»).
Если клиент Telegram старый или подготовка не удалась, открывается обычное окно «Поделиться» со
ссылкой. «Сохранить» отдаёт файл через `downloadFile`: Telegram предлагает сохранить фото в галерею.

Уточнение (раунд 5). Картинка теперь не перерисовывается на canvas, а снимается с настоящего
компонента карты (`html-to-image`), поэтому цвета и узор совпадают один в один. Кадр 4:3
(1200×900: надпись SpinCards и карта со свечением тира): в чате отправителя Telegram обрезал
широкую картинку, 4:3 показывается целиком. Подпись идёт в HTML: текст игрока, ниже «Испытай удачу
в SpinCards» со скрытой реферальной ссылкой, затем строка канала (в админке можно указать ссылку
t.me, тогда строка тоже кликабельна). Сервер принимает только реферальную ссылку самой игры и
экранирует весь текст. Цвета чипа заданы атрибутами SVG, потому что снимок не переносит CSS внутрь SVG.

### D-115. Продление и восстановление по редкости

Раньше цена была процентом от баланса карты, и пустую карту можно было продлить бесплатно. Теперь
цена зависит от редкости и платится с кошелька: база (500 ₽ / 6 $ за Common) × 4 за каждый тир выше
(Rare 2 000 ₽, Epic 8 000 ₽, Legendary 32 000 ₽, Mythic 128 000 ₽) × (1 + 2% за очко редкости
номера, не больше ×5). Восстановление — цена продления × 1,5. Баланс карты не меняется. Числа в
конфиге (`lifecycle.extendPrice`, `lifecycle.restoreMultBp`), формула общая для сервера и Mini App.

### D-116. Скрытая стартовая удача

Игроки жаловались, что начальный баланс трудно раскрутить: при RTP пакета «Базовый» ~98% деньги
просто заканчивались. По решению владельца (2026-10-14) добавлена скрытая удача на шансы Rare+:

- у всех, у кого кошелёк плюс активные карты в валюте прокрута меньше 30 000 ₽ / 350 $, — +100%
  (шансы Rare+ вдвое выше, RTP «Базового» ~103%);
- первые 20 прокрутов любого игрока — +300% (вчетверо, RTP ~112%), независимо от баланса;
- из двух действует больший; оба применяются сверх `boostCapBp`, чтобы не упираться в потолок
  бонусов карты и бафов (внутри потолка буст почти не двигал RTP: +50% давали +2 п. п.).

Баланс берётся до оплаты партии прокрутов. Проданные или сгоревшие карты не считаются, только
активные; считать один кошелёк было бы нельзя: можно держать деньги на картах и жить с бустом.

Удача не видна игроку: в интерфейсе её нет, клиент больше не получает `newbieStep`; на сервере всё
пишется в `spins.rolled_params` (`hiddenBoostBp`). Опубликованные шансы пакетов остаются базовыми:
скрытый буст их только повышает, реальные шансы не ниже опубликованных.

Это сознательное исключение из правила CLAUDE.md «шансы задают только пакет, карта, уровень и
счётчики активности»: добавлен баланс игрока (только в сторону повышения шансов), правило уточнено.
Коридор RTP 85–105% проверяется по обычному игроку (`make sim` без `--balance`); сегмент ниже порога
смотрится отдельно: `make sim ARGS="--pack basic --balance 0"`. Числа в `luck.hidden` конфига и в
админке (раздел «Удача»).

### D-117. Выкладка, бэкапы и алерты (M9)

**Выкладка без сборки на сервере.** `make release` собирает образы `spincards-{api,bot,web,admin}:<коммит>`
под `linux/amd64` на машине разработчика, `make ship HOST=…` передаёт их одним архивом по SSH
(`docker save | ssh docker load`, общие слои идут один раз, ~200 МБ) вместе с папкой `deploy/`, и
запускает `spincards.sh deploy`. Реестр образов не нужен (git remote нет); если появится, `ship`
заменяется на push/pull. На сервере только `/opt/spincards`: compose, Caddyfile, скрипт, `.env`.
Имя бота фронтенд больше не вшивает при сборке: API берёт его из `getMe` (`botUsername` в публичном
конфиге), поэтому один образ годится для любого бота. В production API не стартует с dev-остатками:
http-адресом, пустым CORS, заглушками `__generate__`, паролем Postgres `spincards`.

**Бэкапы — задачи worker, а не отдельный контейнер.** Так переиспользуется проверка ledger, статус
виден в админке, алерты идут тем же путём. В образе API есть `postgresql16-client` (та же версия, что
у сервера). Каждый день в 03:00 UTC `pg_dump -Fc` в `backups/daily` (хранится 7), воскресный ещё и в
`weekly` (хранится 4, жёсткая ссылка без лишнего места). По воскресеньям в 03:30 свежий дамп
восстанавливается во временную базу `<db>_restore_check`, там проверяется, что каждый баланс равен
сумме ledger, и база удаляется. Ручные: `spincards.sh backup | restore-check | restore <file>`
(перед восстановлением снимается страховочный дамп). Копия бэкапов вне сервера — позже (S3).

**Алерты — напрямую через Bot API**, не через бота и очередь уведомлений: так они доходят и когда
бот лежит, и получатель не обязан быть игроком. Получатели — Telegram ID в админке
(«Настройки → Алерты и бэкапы», только owner, с тестовой отправкой). Поводы: бэкап или проверка
восстановления не удались (или нашли расхождения), сервис дважды подряд не ответил на health и
снова поднялся, ≥ 20 неожиданных 5xx за 5 минут, свободно < 10% диска, предохранители RTP/эмиссии.
Одинаковый алерт — не чаще раза в 30 минут (диск — раз в 6 часов). Если упал сам worker, алертов
не будет: для этого внешний мониторинг (UptimeRobot на `/api/health`).

### D-118. Производительность API (M9)

- **Кластер.** API запускает `API_PROCESSES` процессов на одном порту (`node:cluster`, в проде `auto`
  = по ядру); главный процесс только перезапускает упавшие и передаёт SIGTERM. Пул БД на процесс
  10 соединений, `max_connections` Postgres 200 (dev 300 — для нагрузочного теста).
- **Кэши без ожидания пула.** Конфиг, эксперименты и флаги кэшируются на 5 с через
  `RefreshingCache`: устаревшее значение отдаётся сразу, обновление идёт в фоне одним запросом,
  первое чтение прогревается при старте. Раньше обновление внутри транзакции прокрута требовало
  второе соединение и под нагрузкой блокировало весь пул на 10–20 с. После действий в админке
  (активация конфига, флаг) значение перечитывается сразу в этом процессе, в остальных — за 5 с.
- **Сброс нагрузки.** Если в процессе больше 256 запросов одновременно или задержка event loop
  (p99 за секунду) выше 300 мс, новые запросы сразу получают `503 OVERLOADED` без обработки; клиент
  повторяет их как есть (до 3 раз с паузой), ключ идемпотентности тот же. `/health` не отсекается.
- **Гигиена.** Ежедневно (04:00 UTC) удаляются ключи идемпотентности старше 7 дней, refresh-токены
  через сутки после истечения и закрытые сессии админки. Ledger, прокруты и платежи не трогаются.
- **Отложено:** сокращение SQL на прокрут (~48 → ~28) — следующий шаг к 1000 прокрутов/с, замеры в
  `docs/performance.md`.

### D-119. Антифрод (M9)

Переводов между игроками нет, поэтому вывести ценность из твинков можно только комиссией 5% с
прокрутов приглашённого. Со скрытой стартовой удачей (D-116) твинк с балансом ниже порога крутит
с отдачей выше 100% бесконечно, и без ограничений основной аккаунт получал бы по 50 ₽ с каждого
его прокрута. Поэтому комиссия ограничена: не больше 10 000 ₽ (110 $) с одного приглашённого за
весь срок и 20 000 ₽ (220 $) пригласившему в сутки (UTC); остаток не переносится. Числа в
`referral.commission` конфига.

Автоматических блокировок нет: в админке (Игроки → «Подозрительные») список с сигналами для
ручной проверки — ≥ 600 прокрутов за час, ≥ 5 приглашённых за сутки, ≥ 4 аккаунтов с одного IP за
неделю, упор в дневной потолок комиссии (пороги в `antifraud` конфига). IP не хранится: при входе
в Redis на 7 дней пишется HMAC адреса (ключ — JWT_SECRET) и ID игроков с него; это упомянуто в
политике конфиденциальности. Общий IP у мобильных сетей — подсказка, а не доказательство.
Лимиты запросов (по игроку и по IP на входе) уже были на всех маршрутах.

### D-120. Подготовка к открытой бете: баланс, уровни пакетов, админы

- Стартовый кошелёк 30 000 ₽ (было 5 000): тестеры сливали баланс в первый час. Порог скрытой
  удачи (D-116) тот же, 30 000 ₽: новичок стартует ровно на нём, буст «малого баланса» включается
  после первого платного прокрута, а первые 20 прокрутов у него и так буст новичка.
- «Бизнес» открывается с 15 уровня (было 3), «Премиум» с 30 (было 8): с большим стартом игроки
  иначе сразу уходили в дорогие пакеты и сливали всё.
- Лимит обмена валют 5 000 000 ₽ / 55 000 $ в сутки; лимит и стартовый баланс есть в форме
  конфига админки.
- Сессия админки живёт 7 дней, выход после суток бездействия (было 12 часов и час).
- Owner управляет админами (раздел «Админы»): создать с ролью и временным паролем (от 12
  символов; TOTP настраивается при первом входе), сменить роль, отключить, сбросить TOTP. Любая
  смена доступа завершает сессии этого админа. Owner не может понизить или отключить себя, и
  последнего активного owner отключить нельзя. Всё в audit_log.
- Тесты API работают с фиксированным стартом 5 000 ₽ (global-setup), чтобы сценарии вроде «пачка
  из пяти прокрутов не помещается» не зависели от продовых чисел.
- Новые дефолты конфига попадают в прод командой `./spincards.sh config-defaults` (с симуляцией и
  архивом прошлой версии; правки, сделанные в админке, заменяются).

### D-121. Лимит прокрутов с одной карты

С одной карты из холдера можно оплатить не больше 250 прокрутов за окно в 12 часов; окно
открывается первым прокрутом этой картой и у каждой карты своё (выбор владельца). С кошелька
ограничений нет. Пачка, которая не помещается в остаток, отклоняется целиком (`CARD_SPIN_LIMIT`),
Mini App заранее ограничивает размер пачки остатком и показывает, когда карта снова доступна.
Счётчик хранится в карте (`spin_window_started_at`, `spins_in_window`), обнуляется, когда карта
из пула достаётся новому владельцу. Числа в `cardSpinLimit` конфига; правило окна общее для
сервера и Mini App (`chargeCardSpins` в shared).

### D-122. Фильтры истории операций

История кошелька фильтруется по группе операций (прокруты, обналичивание, карты — пополнения,
переводы, продление и восстановление, обмен, бонусы — старт, награда дня, сундучок, колесо,
рефералы, покупки, прочее), по валюте и периоду (1, 7, 30 дней или всё время). Группы — общая
константа `HISTORY_GROUPS` (shared) над причинами ledger; сервер принимает `group`, `currency`,
`days`, неизвестные значения — 400.

### D-123. Номер уникален внутри «банк + редкость»

По решению владельца комбинации номеров могут повторяться у карт разных банков и редкостей:
9777 7777 7777 7777 может одновременно быть у Ruby Epic и у Azure Rare, но не у двух Ruby Epic.
Частичный уникальный индекс теперь по (bank_id, tier, number) для живых карт; генератор проверяет
свободность номера в своей ячейке по всем статусам (пул тоже), чтобы карта из пула не встретила
двойника. Полный дубль (16 одинаковых цифр) делает карту Mythic, поэтому такой номер проверяется
среди Mythic. Правило в CLAUDE.md обновлено.

### D-124. Ежедневные и сезонные задания

По запросу владельца перед открытой бетой (в CLAUDE.md ачивки были «не в v1»).

- **Ежедневные:** три случайных задания из набора на каждый московский день (обновление в 00:00
  МСК), часть открывается с уровня. Деньги в награде растут с уровнем так же, как награда дня
  (+4% за уровень, D-113), плюс опыт, баф или бесплатные прокруты. Невыполненные сгорают.
- **Сезонные:** фиксированный список на сезон (2 недели), рассчитан на среднеактивного игрока:
  ~1 200 прокрутов за 8 игровых дней (по альфе: медиана 340 прокрутов в игровой день). Цели:
  1 000 прокрутов, 100 карт одного банка, 40 Epic+, 5 Legendary, Mythic (самое трудное), 5 карт в
  холдере одновременно, карта в холдере 4 дня, 7 дней со входом, 300 обналичиваний, 500 прокрутов
  картой, 60 красивых номеров, 15 оборотов колеса. Награды фиксированные и крупнее.
- **Как считается:** действия (прокрут, выпавшая карта, обналичивание, холдер, колесо, сундучок,
  награда дня, первый вход за день) сообщают события в своей транзакции, прогресс двигается вместе
  с действием. Холдер (число карт, самый долгий срок удержания) измеряется при его изменении, при
  входе и при открытии заданий. Чистая логика — `advanceQuest`/`pickDailyQuests` в game-core.
- **Хранение:** `quest_progress` (одна строка на игрока, период и задание); цель и награда
  копируются из конфига при выдаче, поэтому смена конфига не двигает цель на ходу. Получение
  награды идемпотентно, деньги — через ledger (`quest`). Набор и числа — `quests` в конфиге.

### D-125. Сезоны и рейтинги

- **Сезон длится 2 недели** (`seasons.lengthDays`). Worker раз в минуту: даёт активному сезону дату
  окончания, а когда она прошла — фиксирует итоги, платит награды топу через ledger
  (`season_reward`), шлёт победителям уведомление в бота и открывает следующий сезон. Owner может
  перенести окончание текущего сезона в админке («Сезоны»).
- **Живёт только сезон:** рейтинг «Сезон» по очкам сезона — сумме редкости всех карт, выпавших за
  сезон (обналичивание очки не отнимает), сезонные задания (D-124). Награды топа по умолчанию:
  1 место 500 000 ₽, 2–3 по 250 000, 4–10 по 100 000, 11–50 по 30 000 (`seasons.rewards`).
- **Живёт всегда:** деньги, карты, уровень, рейтинги «Всё время» (баланс, коллекция) и итоги
  прошлых сезонов в профиле (`season_results`).
- Смена набора банков и дизайнов между сезонами — отдельная задача ближе к сезону 2; постоянная
  коллекция («альбом») — отдельной веткой.
- Метка сборки рейтинга в Redis теперь хранит список типов: релиз с новым типом пересобирает
  рейтинги сразу, а не через час.

### D-126. Альбом — постоянная коллекция

Что живёт всегда, помимо денег и уровня: альбом. В нём остаётся каждая впервые полученная пара
«банк × редкость» и каждый впервые выбитый паттерн номера, даже когда карту обналичили или она
сгорела (`album_entries`, запись в транзакции прокрута; при выкладке заполнен из истории). Сейчас
55 ячеек (8 банков × 5 редкостей + 15 паттернов); банки новых сезонов добавят страницы, поэтому
альбом — главный долгий повод возвращаться. Рейтинг «Альбом» во вкладке «Всё время» считает
заполненные ячейки. Очень активные игроки альфы собрали почти всё — расширять альбом нужно вместе
с банками сезона 2.

### D-127. Второй раунд беты: лимиты и задания

- Лимит карты 500 прокрутов за 12 часов (было 250, D-121); на картах холдера виден остаток, в
  выборе оплаты карты без лимита стоят последними и не выбираются.
- Сундучков копится до 5 (было 3).
- Ежедневных заданий 5 в день из набора 24 (каждый день случайные, часть с уровня); сезонных 30, в
  две ступени, под активного игрока (~3 000 прокрутов за две недели). Сезонные задания, убранные из
  конфига, больше не показываются и не считаются.
- Кнопки экрана подписки стоят в одной колонке по центру.

### D-128. Удача карты от номера

Раньше бонус удачи карты = бонус тира + 2% за каждое очко редкости (тир + номер), не больше 20%.
Очки тира Legendary (25) и Mythic (80) сами упирались в потолок, поэтому обычная Mythic и Mythic с
полным дублем давали одинаковую удачу, а номер «ничего не добавлял». Теперь: бонус тира + 1% за
каждое очко **паттернов** номера, до +50% (полный дубль достигает потолка; хвост 7777 = +40%).
Общий потолок бонусов к шансам Rare+ поднят с +50% до +100%, иначе удача от номера срезалась.
Симулятор: отдача 99–101% при оплате картой в 30% и 90% прокрутов. Уже выданным картам удача
пересчитана миграцией по новой формуле.

### D-129. Альбом — витрина трофеев (вместо D-126)

Альбом из D-126 (автоматический учёт «банк × редкость») не то, что нужно игрокам. Теперь альбом —
витрина: игрок сам кладёт туда карты, которые хочет сохранить и показывать.

- Карта становится **трофеем** (`status = trophy`): её баланс обналичивается в кошелёк с обычной
  комиссией, место оплачивается из кошелька по редкости (5 000 ₽ за Common, ×√10 за тир — 500 000 ₽
  за Mythic, плюс 1% за очко паттернов номера до ×3), карта больше не участвует в игре, не сгорает,
  не возвращается в пул, номер остаётся за игроком. Трофеи переживают смену сезона.
- 5 бесплатных мест (`showcase.freeSlots`), дополнительные — за Stars (`extraSlotStars`); пока
  Stars выключены, кнопка показывает «скоро».
- Трофеи видны в публичном профиле игрока; рейтинг «Альбом» — сумма редкости трофеев.

### D-130. Коллекция сезона

Бывшая сетка альбома стала «Коллекцией сезона»: какие пары «банк × редкость» игрок выбил в текущем
сезоне (по его прокрутам сезона). В холдере — полоса прогресса, по нажатию — вся сетка с пустыми
ячейками. С банками нового сезона сетка сменится. Таблица `album_entries` (D-126) больше не
используется интерфейсом и оставлена как история.

### D-131. Переводы игрокам по юзернейму

По решению владельца (механики друзей пока нет). Деньги из кошелька в кошелёк той же валюты по
@username (без учёта регистра). Ограничения «мягкие», в конфиге `p2p`: с 3 уровня у отправителя и
получателя, комиссия 2% (сгорает), минимум 100 ₽ / 1 $, до 500 000 ₽ / 5 500 $ в сутки на отправку
и отдельно на получение. Получатель узнаёт о переводе от бота. Антифрод: сигнал «переводы от N
игроков за сутки» (`antifraud.p2pSendersPerDay`, по умолчанию 3) — главный признак фарма твинками
(скрытая удача новичков D-116 + перевод на основной аккаунт).

Блокировки: строка ключа идемпотентности вставляется первой и берёт KEY SHARE на строку
отправителя, поэтому `FOR UPDATE` на обоих игроков давал взаимоблокировку встречных переводов.
Вместо него — `pg_advisory_xact_lock` по обоим игрокам в одном порядке; кошельки по-прежнему
блокирует ledger. Тест: 10 встречных переводов одновременно, ledger сходится.

### D-132. Сезон: очки, обнуление и перенос (заменяет денежные награды D-125)

- **Очки сезона** = редкость всех выбитых за сезон карт + 1 очко за каждые 1 000 ₽ капитала
  (кошельки + живые карты в рублях) + 20 очков за уровень (`seasons.score`). Одна формула
  (`seasonScore`, game-core) для рейтинга «Сезон», профиля и итогов. В рейтинге только игравшие в
  сезоне.
- **Конец сезона** (worker, режим техработ на время подсчёта; включённый админом режим не
  снимается): места и медали (топ-1/3/10/50, полная коллекция сезона), уведомление в бот. Затем
  новый сезон и **обнуление каждого игрока** отдельной транзакцией: живые карты сгорают и больше не
  выпадают (трофеи альбома остаются), все кошельки → 0 через ledger (`season_reset`), уровень 1 и
  0 EXP, стартовые деньги = `startingBalance` + перенос `min(очки × 10 ₽, 200 000 ₽)`
  (`season_start`). Признак — `users.money_season_id`; шаг повторяемый, после сбоя доигрывается.
  Остаются: альбом, медали, купленные холдеры, бафы, бесплатные прокруты, счётчики удачи.
- Текущий сезон «Бета» завершится 28 октября по этим правилам; при выкладке никто не обнулялся.

### D-133. Медали и ачивки

Каталог в конфиге (`achievements`): постоянные (первая Epic/Legendary/Mythic, полный дубль,
лестница из 8+, хвост 7777, 1 000 и 10 000 прокрутов, 50 уровень, миллионер, 5 трофеев, 50 заданий)
и сезонные (места, полная коллекция — каждый сезон заново). Награда — деньги через ledger
(`achievement`) и опыт, выдаётся один раз (`user_achievements`, уникально по игроку, ачивке и
сезону). Проверка — в транзакции прокрута, получения задания, трофея; при открытии медалей — ещё и
по всей истории прокрутов (ретроактивно, поэтому тестеры альфы получат медали за прошлые карты).
Новые медали показываются уведомлением после прокрута, все — в профиле. В тестах API ачивки
по умолчанию выключены (точные балансы сценариев), отдельный тест их включает.

### D-134. Тексты в админке

Owner правит основные тексты без релиза (раздел «Тексты»): экран подписки, правила и
конфиденциальность в Mini App; приветствия, справку, ответы о подписке, часть уведомлений и
кнопки бота. Список — `EDITABLE_TEXTS` (shared), правки — в `app_settings.texts`, по умолчанию
остаются тексты i18n. Mini App получает правки с публичным конфигом и применяет поверх i18n (в том
числе на экране подписки); бот раз в минуту забирает свои через внутренний маршрут. В правке
разрешены только простые подстановки `{name}`, которые есть в исходном тексте: так опечатка не
сломает ICU-разметку (`TEXT_PLACEHOLDER_INVALID`). Под ответом на /start можно добавить свою
кнопку-ссылку (текст + https-адрес), например на канал. Кэш скомпилированных сообщений i18next-icu
сбрасывается при применении правок, иначе подмена не была бы видна.

Попутно: тест TOTP иногда падал на границе 30-секундного окна (повторялся новый код, а не тот же);
исправлен тест, сервер был прав.

### D-135. Сильнее бонус удачи тира карты

Бонус тира при оплате картой был почти незаметен (Rare +3 %, Epic +6 %, Legendary +10 %, Mythic
+15 % к весу Rare+). Новые значения: Rare +8 %, Epic +15 %, Legendary +25 %, Mythic +40 %; бонус
номера не менялся (+1 % за очко, до +50 %), общий потолок буста прежний (+100 %). Симулятор
(300 000 прокрутов): при 100 % оплаты картой RTP 96,9–100,1 %; худший сценарий (уровень 30, баф
+20 %, всегда картой) 97,4–104,6 %, в коридоре. Вариант 10/20/35/50 % выводил «Бизнес» в этом
сценарии на 106 % и отклонён. На проде значения приходят через `./spincards.sh config-defaults`.

### D-136. Подсветка редкости на ленте прокрута

Карты на ленте светятся рамкой своего тира (Rare и выше), чтобы прокрут был напряжённее. Выпавшая
карта светится своим настоящим тиром с самого начала: результат уже решён сервером, анимация его
только показывает. Тиры остальных карт ленты — декорация, разыгранная на клиенте по опубликованным
шансам пакета (детерминированно от id карты, чтобы перерисовка не меняла ленту). Соседи точки
остановки никогда не редче выпавшей карты: лента не должна изображать «почти выпало» (правило
near-miss, TZ 4.8). Свечение статичное и рисуется один раз в слой ленты, на FPS не влияет.

### D-137. Медали в рейтинге

В строке рейтинга и в профиле игрока под именем видны до трёх медалей. По умолчанию это самые
редкие из полученных: меньше всего обладателей (кэш на 10 минут), при равенстве — с большей
наградой. В профиле игрок нажатием выбирает свои три (`users.pinned_medals`, POST /v1/settings
`pinnedMedals`); показываются только реально полученные, лишние id игнорируются, больше трёх —
`VALIDATION_FAILED`. Пустой выбор возвращает «самые редкие». У каждой медали показано, у какой доли
игроков она есть.

### D-138. Бонус удачи карты считается по текущему конфигу

Раньше бонус удачи записывался в карту при выпадении и не менялся, поэтому после D-135 старые
карты давали прежний бонус, а расшифровка на экране карты (тир из нового конфига) с ним не
сходилась («+16 %, тир +40 %, номер +0 %»). Теперь бонус при оплате и в интерфейсе считается из
тира и узоров номера по активному конфигу, как и остальные числа экономики. Поле
`cards.luck_bonus_bp` остаётся историей значения на момент выпадения.

### D-139. Удаление карты из альбома

Игрок может убрать трофей из альбома (нажатие на карту в альбоме → подтверждение), чтобы
освободить место. Карта уходит из игры навсегда (`cashed`, без владельца) и больше не выпадает;
цена места не возвращается (баланс карты уже ушёл в кошелёк при сохранении), ledger не меняется.
Операция идемпотентна, чужие и не-трофейные карты — `CARD_NOT_FOUND`.

### D-140. Прогрессия сезона: цены и открытие пакетов

Симулятор прогрессии (`make progression`: сезон по дням для игроков на 60, 250, 600 и 1 500 карт в
день, реальный движок прокрута и награды по ожиданию) показал две проблемы. Повседневный игрок за
14 дней не доходил до 15-го уровня и весь сезон играл только «Базовым». Остальные открывали пакеты,
но 80 % прокрутов оставались в «Базовом»: «Бизнес» стоил ×15 от «Базового», кошелёк медианного
игрока весь сезон держался около 70 000 ₽, и роста денег игрок не чувствовал.

Изменения (только конфиг): «Бизнес» 5 000 ₽ / 56 $ (было 15 000 ₽), с 10-го уровня (было 15),
30 EXP за прокрут (было 60); «Премиум» 40 000 ₽ / 440 $ (было 100 000 ₽), с 20-го уровня (было 30),
90 EXP (было 200). Базовые лимиты карт уменьшены пропорционально цене, поэтому RTP прежний
(95–100 %, худший сценарий 104,6 %); баффы дешевеют сами, их цена считается от пакета. Опыт за
дорогие пакеты снижен, иначе активные игроки упирались бы в 300-й уровень.

Результат (медианы за сезон):

| Игрок           | Бизнес | Премиум        | Уровень к 14-му дню | Прокруты: Базовый / Бизнес / Премиум | Кошелёк              |
| --------------- | ------ | -------------- | ------------------- | ------------------------------------ | -------------------- |
| 60 карт/день    | день 7 | день 14 у 73 % | 20                  | 53 / 46 / 1 %                        | 30 тыс. → 150 тыс. ₽ |
| 250 карт/день   | день 2 | день 4         | 48                  | 40 / 50 / 11 %                       | → 96 тыс. ₽          |
| 600 карт/день   | день 1 | день 2         | 83                  | 38 / 45 / 18 %                       | → 100 тыс. ₽         |
| 1 500 карт/день | день 1 | день 1         | 160 (p90 237)       | 32 / 40 / 28 %                       | → 630 тыс. ₽         |

Было: 14 / 42 / 67 / 110 уровень, «Базовый» 100 / 80 / 82 / 78 % прокрутов. На проде значения
приходят через `./spincards.sh config-defaults`.

### D-141. Коридор RTP держится при оплате лучшей картой

На проде фактический RTP всех пакетов был 106–127 % (по выданному, до комиссии), «Бизнес» за час
дал 290 % и встал на паузу. Причина: игроки платят лучшей картой (выбор оплаты сам ставит её
первой, пополнение карты бесплатно), а проверка конфига мерила «среднюю» карту (30 % оплат
случайной картой на 1-м уровне). Удача карты поднимает и тиры, и узоры номера; при бонусе
+40…+100 % RTP был 108–127 %. Проблема была и до D-135, повышение бонусов тира и D-138 (бонус
по текущему конфигу для старых карт) её усилили.

Изменения:

- общий потолок буста `luck.boostCapBp` +40 % (было +100 %): карта, бафы и счастливый прокрут
  вместе дают не больше;
- бонус тира карты: Rare +5 %, Epic +10 %, Legendary +15 %, Mythic +20 %; номер +1 % за очко,
  до +20 % (было до +50 %); бонус карты не показывается выше потолка;
- базовые лимиты карт: «Базовый» ×0,92, «Бизнес» ×0,90, «Премиум» ×0,96;
- проверка перед активацией (админка и `config-defaults`) прогоняет каждый пакет ещё и в
  сценарии «лучшая карта на потолке удачи» на уровне `simulation.bestCardLevel` (100); конфиг
  не активируется, если любой сценарий вне коридора;
- `make sim ARGS="--card-luck 40"` — все прокруты лучшей картой; `make progression` моделирует
  игрока, который платит самой удачливой из своих карт.

Результат: обычный игрок (кошелёк и случайная карта) 88–91 %, лучшая карта на потолке
101–102,6 % (RUB и USD). Разница около 12 п. п., удача карты ощутима. Прогрессия (медианы к 14-му
дню): 60 карт в день — 19-й уровень, «Бизнес» с 7-го дня; 250 — 48-й, «Премиум» с 5-го; 600 —
89-й; 1 500 — 193-й. У гриндеров выше 150-го уровня комиссия обналичивания меньше и RTP подходит к
105 %, это принято как награда за объём.

### D-142. Экраны после деплоя

После деплоя вкладки «Холдер» и «Кошелёк» (и любой ленивый экран) переставали открываться у тех,
у кого Mini App был открыт или закэширован. Экраны грузятся отдельными файлами с хешем в имени;
в образе новой версии старых файлов нет, а сервер на неизвестный путь отдавал `index.html`
(SPA-fallback) без `Cache-Control`. Старая страница получала HTML вместо модуля, и экран не
загружался. Теперь `index.html` отдаётся с `Cache-Control: no-cache`, отсутствующий файл в
`/assets/` — честный 404, а клиент при ошибке загрузки экрана один раз перезагружает страницу и
получает новую версию (повторная ошибка в течение 30 секунд показывается как ошибка, без цикла).

### D-143. Сезон на главном экране

`/v1/me` отдаёт текущий сезон (`season: { name, endsAt }`); на главном экране под логотипом —
плашка «Сезон «Бета» · ещё N дней», по нажатию открывается сезонный рейтинг.

### D-144. Больше редактируемых текстов

В админке («Тексты») теперь правятся и тексты экрана «Шансы» (вступление, удача, красивые номера,
«почти выпало», рост наград), пояснение альбома и заголовок /rules в боте. Правила игры — общий
текст: правка видна и в Mini App, и в ответе бота на /rules (бот применяет правки любого
пространства имён, список общих текстов — `BOT_SHARED_TEXTS`). В правила по умолчанию добавлено,
что игра в бете и баланс (шансы, цены, награды, лимиты, уровни) может меняться.

### D-145. Бот: поддержка, реферальная ссылка, посты канала, зелёная кнопка

- Под приветствием /start зелёная кнопка «Играть» (стиль кнопки `success` из Bot API), ниже
  «Пригласить друзей» и «Поддержка».
- `/ref` и кнопка: ссылка `t.me/<бот>?startapp=ref_<код>` (та же, что в профиле игры) и кнопка
  «Поделиться ссылкой».
- Поддержка через Telegram-группу владельца (решение владельца). Любое сообщение игрока в личке
  (не команда) уходит в группу с заголовком `🆘 Имя @ник · #id<telegramId>`; фото, видео и файлы
  копируются с тем же заголовком в подписи. Ответ (reply) на сообщение бота в группе бот
  пересылает игроку. Состояния нет: адресат берётся из тега `#id`. До 10 сообщений в час с одного
  игрока (защита от спама). Id группы задаётся в админке («Тексты» → «Бот»), его присылает
  команда `/chatid` в группе. Без группы игрок видит «Поддержка пока недоступна».
  Уточнение владельца: в группу уходят только сообщения после кнопки «Поддержка» (или /support):
  открывается обращение на 15 минут с последнего сообщения, кнопка «Завершить обращение» его
  закрывает. Остальные сообщения в чате с ботом получают подсказку с кнопкой «Поддержка». В профиле
  Mini App кнопка «Написать в поддержку» открывает бота по ссылке `?start=support` сразу в режиме
  обращения.
- Посты канала: бот получает `channel_post` из каналов, где он администратор; api ставит пост в
  очередь только для каналов из настроек подписки и только при включённой опции в админке. Пост
  пересылается (forward) игрокам с включёнными уведомлениями, один раз на игрока
  (`dedupe_key`); тихие часы соблюдаются, дневной лимит игровых напоминаний на посты не действует.
- Тексты бота (поддержка, реф-ссылка, кнопки) правятся в админке.

### D-146. Покупки за Telegram Stars

Решение владельца: Stars включены для всех игроков беты. Каталог живёт в конфиге экономики
(`stars`, а также `holders[].starsPrice`, `showcase.extraSlotStars`,
`chest.levels[].upgradeStarsPrice`); id товара — `<вид>` или `<вид>:<ref>`:

- `buff:<id>` — бафф удачи на 20 прокрутов любого пакета, без дневного лимита, баффы
  складываются. Исключение из правила «шансы не зависят от оплаты» по решению владельца, но в
  рамках общего потолка удачи (+40 %, D-141): за звёзды нельзя получить удачу выше потолка, и
  коридор RTP «лучшая карта на потолке» по-прежнему проверяется перед активацией конфига;
- `free_spins:<id>` — бесплатные прокруты сверх запаса;
- `holder:<id>` — холдер сразу, без ожидания уровня;
- `album_slot` — место в альбоме, без лимита;
- `chest_upgrade` — следующий уровень сундучка (альтернатива покупке за монеты);
- `wheel_now` — колесо фортуны доступно сразу (не продаётся, пока оно и так готово);
- для карты: `card_limit_reset` (сброс окна лимита прокрутов), `card_extend` (ещё одно продление
  сверх разового лимита), `trophy` (в альбом без оплаты монетами; баланс карты уходит в кошелёк).

Цена считается на сервере при выставлении счёта и проверяется ещё раз на pre-checkout; если к
моменту зачисления товар выдать нельзя (карта сгорела, альбом заполнен), звёзды автоматически
возвращаются (`refundStarPayment`), платёж помечается `refunded`. Бесплатных мест в холдере
теперь 4 (было 5). Платные пакеты за звёзды (VIP) по-прежнему выключены.

### D-147. Удача — шкала от 0 до 100

Решение владельца: проценты удачи скрыты, игрок видит одно число «Удача N / 100».

- Удача прокрута = (очки карты, которой платят + очки бонусов) × множитель звёздного бафа, не
  больше 100. Платёж с кошелька — без очков карты.
- Очки карты: тир (Common 5, Rare 12, Epic 22, Legendary 32, Mythic 42) + номер (1 очко за очко
  редкости узоров, до 45). Лучшая карта — 87: одной картой 100 не набрать.
- Бесплатные бонусы (колесо, сундучок, награды дня, задания) дают «+5/+10/+15 удачи на 10
  прокрутов» — очки, не множитель.
- Баффы за звёзды — множитель удачи на 60 минут: ×1,5 (15 ⭐), ×3 (30 ⭐), «максимум» ×20 (60 ⭐,
  даже Common с удачей 5 даёт 100). Действует самый сильный, повторная покупка того же продлевает
  время, лимита покупок нет. Баффы за игровую валюту убраны.
- Внутри одно очко = +0,7 % к весам Rare+ и красивых номеров (`luck.pointBp`), удача 100 = +70 %.
  Скрытая стартовая удача новичков и игроков с малым балансом (D-116) работает сверх неё —
  это и даёт «упал — поднялся».
- Коридор RTP 85–110 %. Базовые лимиты карт снижены (Базовый ×0,95, Бизнес ×0,985, Премиум ×0,96).
  Проверка конфига: обычный игрок 86,5–89 %, лучшая карта на удаче 100 и 100-м уровне 99–107 %.
- Прежняя «Шкала удачи» до счастливого прокрута переименована в «До счастливого прокрута».
- В базе у бонусов появились `luck_points` и `multiplier_bp`; работающие бонусы конвертированы
  (1 % → 1 очко). У карты в `luck_bonus_bp` теперь хранятся очки на момент выпадения (история),
  живое значение считается по конфигу (D-138).

Прогрессия (`make progression`, новые игроки, оплата лучшей картой): 60 карт в день — 20-й
уровень, «Бизнес» с 7-го дня, «Премиум» к концу сезона у половины; 250 — 45-й уровень, «Премиум» с
5-го дня; 600 и 1 500 — сильный разброс (p10–p90: 48–147 и 44–246 уровень): кто-то проседает
до бесплатных прокрутов и выбирается обратно, кто-то быстро растёт.

### D-148. Полный дубль: девятка и 15 одинаковых цифр

Номер всегда начинается с 9, поэтому раньше полным дублем мог быть только 9999 9999 9999 9999.
По решению владельца полным дублем считается и «9 + 15 одинаковых цифр» (9555 5555 5555 5555,
9000 0000 0000 0000 и т. д.): Mythic, ×100 (с общим потолком множителя), 500 очков редкости.
9777 7777 7777 7777 проходит проверку Луна и поэтому не выдаётся никогда. Чтобы полный дубль не
стал выпадать чаще (вариантов стало девять, и правило уникальности реже мешает), веса узоров
умножены на 10, а вес полного дубля оставлен 1: частоты остальных узоров не изменились, RTP в
коридоре (обычный игрок 86–87 %, лучшая карта на удаче 100 — 102–108 %).

Проверка конфига перед активацией гоняет теперь 300 000 прокрутов на пакет и сценарий (было
50 000): при 50 000 один полный дубль сдвигал RTP на 6–7 пунктов, и проверка то пропускала, то
отклоняла один и тот же конфиг. На большой выборке «Базовый» у обычного игрока оказался 84 %,
поэтому его базовые лимиты подняты на 3 % (обычный игрок 88 %, лучшая карта 103–105 %).

### D-149. Выход из альфы: новый сезон «Бета» с чистого листа

Решение владельца: сезон «Бета» идёт ровно неделю, 16.10.2026 22:00 – 23.10.2026 22:00 МСК
(следующие сезоны — по-прежнему `seasons.lengthDays`). Перед стартом все игроки начинают заново:

альбома) нет владельца, кошельки обнулены и получают стартовые деньги через ledger

серия наград дня, бонусы удачи, счётчики гарантий, купленные холдеры и места альбома, а также
связи «кто кого пригласил» сброшены. История (ledger, прокруты, платежи, переводы, события)
остаётся. Инструмент — `node dist/ops/season-launch-cli.js` (без `--confirm` только считает),

### D-150. Бесплатный холдер всегда у игрока

Бесплатный (стартовый) холдер остаётся на 4 места (владелец сначала попросил 1, но причина была в
пропавших местах, а не в размере). Стартовый холдер теперь считается у каждого игрока всегда, даже

### D-151. Медали только по прокрутам текущего сезона

После запуска «Беты» (D-149) медали за тиры и узоры вернулись «задним числом»: проверка при
открытии профиля смотрела все прокруты игрока, в том числе альфы. Теперь она учитывает только

### D-152. Статистика без альфы

В конфиге `analytics.since` — момент, с которого считается статистика админки: для беты
16.10.2026 22:05:05 МСК, сразу после сброса (D-149). Дни целиком раньше не хранятся (строки
`daily_stats` удаляются плановым пересчётом), день старта считается только после этого момента,
поэтому обнуление кошельков альфы и стартовые деньги в эмиссию не попадают. Оповещения защиты из
альфы в админке тоже не показываются. История в базе (события, прокруты, ledger) не трогается.

### D-153. Проверка подписки для пришедших по ссылке

Telegram на `getChatMember` отвечает `PARTICIPANT_ID_INVALID` (или «user not found») для того, кого
нет в канале, особенно если человек пришёл по ссылке прямо в Mini App и не открывал бота. Раньше
любая ошибка Telegram пропускала игрока (чтобы неверная настройка не заблокировала всех), и за двое
суток так прошло 114 проверок. Теперь эти ответы значат «не подписан»; прочие ошибки (бот не админ
канала, канал не найден) по-прежнему пропускают. Mini App не показывает игру, пока ответ о
подписке не пришёл.

### D-154. В рейтинге у каждого своё место

Раньше игроки с одинаковыми очками делили место (например, два вторых), и последнее призовое место
могли занять двое. Теперь места уникальны: при равенстве выше тот, кто раньше набрал этот результат.
Момент, когда игрок вышел на текущее значение, хранится в Redis рядом с рейтингом и обновляется
только при изменении значения; если его нет (старые записи), выше более старый аккаунт. По тому же
правилу считаются итоговые места сезона и медали за топ-3.

### D-155. Игра проще для новичков

### D-156. Все начинают с рублей

Владелец: доллар остаётся второй валютой (на него можно переключиться и играть), но разделения на

в рублях).

Для тех, кто уже начал сезон так, есть разовый инструмент
`node dist/ops/region-merge-cli.js --reason "…"` (без `--confirm` только считает): игрок переводится в
RU и, если ещё не получал стартовые рубли текущего сезона (ни при регистрации, ни при старте), получает

### D-157. Подписка на канал — задание, а не вход в игру

Владелец: обязательную подписку на канал (D-110) отключают в админке (Настройки → Подписка →
«обязательная» выкл.), а за подписку дают награду. Отдельное сезонное задание «Подпишись на канал»
стоит над вкладками заданий и пропадает, когда награда получена. Каналы берутся из тех же настроек
подписки (список в админке); пока список пуст или в конфиге нет `quests.channel`, задания нет.

- Награда в конфиге: `quests.channel.reward` — 50 000 ₽ (5 000 000), в долларах $550 (55 000) в той
  же пропорции, что у сезонных заданий. Раз в сезон: строка `quest_progress` с `questId=channel_sub`
  (`kind=season`, `period=seasonId`), уникальный индекс не даёт получить дважды. В счётчик и бейдж
  обычных заданий она не входит (её нет в `quests.season`).
- «Проверить» (`POST /v1/quests/channel/claim`, идемпотентно) спрашивает Telegram сразу, без кэша,
  тем же `getChatMember`, что и D-153. В отличие от обязательной подписки, ошибка Telegram здесь
  значит «не подписан» (`CHANNEL_NOT_JOINED`): награду не платим наугад.
- Отписка после получения награды ничего не отнимает; в новом сезоне задание появляется снова.

### D-158. Приглашать выгодно: награды за друзей и задание «Пригласи друзей»

Владелец: сейчас главное, чтобы люди хотели приглашать.

- Реферальные награды: пригласившему 30 000 ₽ (было 0), другу 10 000 ₽ (было 5 000 ₽); в долларах

  сутки» в админке остаётся.
- Доля с прокрутов друга: 10 % (было 5 %) в течение 30 дней, лимиты выше: 50 000 ₽ с одного друга
  (было 10 000 ₽) и 100 000 ₽ в сутки на пригласившего (было 20 000 ₽). «Побольше» владелец не уточнил,

### D-164. Прокрут: все карты сразу, цифры открываются по одной

Владелец: вместо лент — сразу все карты пачки (×1…×4). Карты переливаются цветами редкостей, номер
открывается слева направо по одной цифре (110 мс), закрытые цифры и баланс случайно бегают; когда

### D-166. Баланс в шапке и пополнение кошелька перед покупкой

Владелец. Шапка: на главной — баланс того, чем платится прокрут (кошелёк или выбранная карта), на
остальных экранах — «Всего»: кошелёк плюс карты валюты региона. Покупки за монеты идут с кошелька;
если кошелька не хватает, а с картами (за вычетом комиссии обналичивания) хватает, вместо покупки
открывается шторка «Пополните кошелёк»: что покупка идёт с кошелька, сколько нужно и сколько есть, и

### D-169. Мини-игры: минёр, плинко, орёл и решка, 21

2026-10-28, по просьбе владельца. Четыре мини-игры на монеты из кошелька, плитками в «Ещё». Чистый
случай: `crypto.randomInt` на сервере, удача, pity и стартовая удача новичка не действуют. Результат
каждого хода считает сервер до анимации; мины, клетка «SpinCards» и колода 21 лежат в
`mini_game_rounds.state` и уходят клиенту только после конца раунда. Ставка и выигрыш — проводки
`minigame_bet`/`minigame_win` в той же транзакции под `lockPlayer`, всё идемпотентно.

- Ставка: от `minBet` (1 ₽ / 1 цент) до `maxBetShareBp` = 35 % баланса кошелька в этой валюте на момент
  ставки. Плинко — лимит на все шары вместе (ставка за шар × шары, до 30). Удвоение в 21 ставит
  исходную ставку ещё раз, ограничено только балансом.
- Минёр: поле 12 / 24 / 48 клеток, мин 1–3 / 1–8 / 1–20, одна клетка «SpinCards». Забрать выигрыш можно
  в любой момент после первой клетки, все пустые открыты — выплата сама. «Шанс на победу» — шанс, что
  следующая клетка пустая. Бонус +50 % к выигрышу в момент находки. Если бонус просто умножал бы выплату,
  выгодно было бы забирать сразу после него (возврат до 117 %). Поэтому лестница честная на каждом шаге:
  пока бонус не найден, шаг растёт в (осталось)/(пустых осталось + b), находка даёт ×(1 + b), после —
  (осталось)/(пустых осталось). Возврат ровно 97 % (`houseEdgeBp` 300) при любой тактике.
- Плинко: 8 / 12 / 16 рядов, отскок 50/50, множители симметричны: по краям ×10, в центре ×0,1; возврат
  96,8 / 97,3 / 97,3 %.
- Орёл и решка: ×1,94 (97 %).
- 21: шуз из 6 колод, перемешивается на каждую раздачу; дилер стоит на любых 17, блэкджек 3:2, удвоение
  на двух картах; без сплита и страховки. Блэкджек у игрока или дилера с раздачи закрывает раунд сразу.
  Возврат при базовой стратегии около 99,1 %.
- Мини-игры не дают опыта, очков сезона, заданий и мест в рейтинге.
- Раунд, оставшийся открытым при смене сезона, закрывается без выплаты (`expired`): деньги сезона
  обнулены (D-132), выплата перенесла бы их в новый сезон.
- Включение: флаг `minigames_enabled` (по умолчанию выключен). Раздел `minigames` в схеме необязательный,
  но `parseConfig` дополняет старые версии значениями `DEFAULT_GAME_CONFIG`, поэтому открывает игры
  только флаг. На проде включено 2026-10-28: конфиг v23 (v22 + `minigames`), флаг в `audit_log`. Симуляция конфига проверяет возврат каждой игры, сложности, числа мин
  и момента «забрать» в коридоре 85–110 %. Монеты не продаются за реальные деньги и Stars (подтвердил
  владелец), поэтому ставки на них допустимы.

### D-170. Крафт карт

- 4 (`craft.cards`) отложенные активные карты одной редкости ниже Mythic и одной валюты → одна новая.
  Балансы карт уходят в кошелёк с комиссией уровня, затем списывается плата `craft.fee[тир]`
  (`craft_fee`). Сервер (`crypto.randomInt`) решает шанс `craft.successBp[тир]` (Common 70 %, Rare 55 %,
  Epic 40 %, Legendary 25 %, решение владельца «шанс зависит от тира»): удача — новая карта на тир выше,
  неудача — новая карта той же редкости. Новая карта сразу отложена, базовый лимит из `craft.baseLimit`,
  номер новый (как при выпадении, полный дубль даёт Mythic). Использованные карты — статус `crafted`,
  история в `card_crafts`. Очки сезона и коллекция за крафт не начисляются (значение по умолчанию).
- Симуляция конфига проверяет: средний баланс новой карты / плата в коридоре 85–110 % для каждого тира
  и валюты (по умолчанию ~97 %). Шансы и платы опубликованы на экране крафта. Флаг `craft_enabled`.
