# Производительность: замеры и план

Цель (согласована 2026-10-13): **≥ 1000 прокрутов/с, p95 ≤ 300 мс** на машине разработки, без нарушений
баланса и уникальности номеров (ориентир 10–20 тыс. одновременно играющих). Работы отложены до M9.

**Узкое место — один Node-процесс (одно ядро).** Во время прогона: Node ~117% CPU, Postgres ~88% (одно ядро
из 14), соединения в `idle in transaction` (ждут JS-поток). Оговорка: генератор нагрузки сейчас работает
в том же процессе, что и api, и забирает часть CPU.

**SQL на цикл «прокрут + обналичить»: ~48 запросов.** Лишнее: двойное чтение пользователя, отдельная
проверка ключа идемпотентности, SELECT бана на каждый запрос, SELECT FOR UPDATE + UPDATE на каждую проводку,
`SET TRANSACTION` в каждой транзакции, два запроса для сезонной статистики, обновление бафов без бафов.

**Найден и исправлен баг пула (D-118).** Кэши флагов и конфига при истечении шли в базу через общий
пул, в том числе изнутри транзакции прокрута. Под нагрузкой все соединения оказывались заняты
транзакциями, ждущими ещё одно соединение: всё вставало на 10–20 с и падало с `INTERNAL_ERROR`.
Теперь кэш отдаёт прошлое значение и обновляется в фоне одним запросом; регрессионный тест
`test/pool.test.ts` (пул в одно соединение) воспроизводит баг на старом коде.

**Итог.** Цель p95 ≤ 300 мс выполнена на 4 процессах при ~490 прокрутах/с. Цель 1000/с не достигнута:
от 8 процессов узким местом становится Postgres и число запросов на прокрут (~48), а не Node.
Для беты запаса много (100 непрерывно жмущих — это тысячи живых игроков). Следующий шаг к 1000/с —
пункт 2 плана ниже (меньше запросов), он трогает проводки ledger и делается отдельно, с замерами.

## План (M9)

1. ✅ **Кластер api:** N процессов Node на одном порту (`API_PROCESSES`, в prod по числу ядер, в dev 1);
   пул БД на процесс, `max_connections` Postgres под сумму.
2. **Меньше запросов (~28 вместо ~48):** ledger через атомарный `UPDATE … SET balance = balance + Δ
WHERE … AND balance + Δ >= 0 RETURNING` (та же блокировка строки) и одну вставку журнала; блокировка и
   чтение игрока одним запросом; идемпотентность без предварительного SELECT; кэш статуса бана 10 с
   (мгновенный сброс из админки в M8); `INSERT … ON CONFLICT` для счётчиков и статистики; без лишнего
   `SET TRANSACTION`; rate limit одним запросом к Redis.
3. ✅ **Postgres в prod:** `max_connections`, `shared_buffers`, `effective_cache_size`; `synchronous_commit`
   остаётся включённым; EXPLAIN горячих запросов.
4. ✅ **Защита от перегрузки:** быстрый `503 OVERLOADED` при превышении числа запросов в работе или задержки
   event loop; клиент повторяет с тем же `idempotencyKey`; таймауты на proxy.
5. ✅ **Гигиена:** ежедневная очистка ключей идемпотентности старше 7 дней и истёкших refresh-токенов.
6. ✅ (частично: кластер, отдельный процесс генератора) **Нагрузочный тест:** генератор отдельно от api, api кластером как в prod, режим разгона до предела
   при p95 ≤ 300 мс, смесь действий (прокрут, hold, оплата картой, обналичивание, повторы), CPU api и
   Postgres в отчёте.
